What is Audio Processing?
------------------------------------------------------------------------------
At a basic level, audio processing takes N channels of audio input, optionally
splits that into additional channels, applies processing to each channel, and
finally sends those channels to an audio output. Like this:

   INPUT --> ROUTING and DSP --> OUTPUTs

The system configuration file of GSASysCon describes these steps using an easy
to read and relatively free-form format.

The sections below will introduce the basics of the system configuration file
structure and format. This begins with how to specify the audio input source and
output sink, proceeds with how to set up the internal audio flow (routing), and 
then covers how to implement DSP processing on each audio channel.


Setup/Configuration - Hardware DSP vs. GSASysCon
------------------------------------------------------------------------------
For most hardware DSPs (e.g. miniDSP), the signal routing as well as the places
that DSP can be used along the path between inputs and outputs, is at least 
partially fixed. It was chosen by the manufacturer, e.g. when they were 
programming the hardware with SigmaStudio. The remaining blanks for DSP and 
perhaps a routing matrix are left for the user to complete, but the overall
framework is already there and chosen for you.

GSASysCon does not give you anything for free. There is no existing framework to
fill in. The user must explicitly tell GSASysCon what sort of signal routing to
use. It's an extra step, but gives you much more flexibility compared to a fixed
routing scheme plus N DSP filters. This means that the first step in writing a 
GSSysCon system configuration is to write down the routing, from the input 
channels to output channels. Luckily this is often very much the same, over and 
over again, and once you understand the basic concept it becomes very easy to 
write down the signal flow and processing. 


Discovering Audio Inputs and Outputs Available from the OS:
------------------------------------------------------------------------------
Audio processing happens between inputs and output, so an important task for the
user is to identify these properly. In order to specify an audio source in the 
system configuration file you have to know what is available to you via the OS. 
This will often be an ALSA card or device or Pipewire-PulseAudio (pulsesrc). 
Below is a brief overview of how to collect info on the audio sources that are 
present on your hardware. If you are familiar with this, you can skip to the 
next section. 

To see a list of ALSA inputs, at an OS command prompt type:
   arecord -l
or
   arecord -L

To get a list of the names of GSASysCon inputs from the PulseAudio server as 
well as from pipewire-pulse, run this command:
   pactl list | grep -A2 'Source #' | grep 'Name: ' | cut -d" " -f2

Under both Pipewire and PulseAudio you can set all of the outputs devices to be
"off" (e.g. using pavucontrol), Pipewire/PulseAudio creates a new "fake" sink 
with a monitor and you can use this device as input by setting the system input 
as follows:
  SYSTEM_INPUT = pulsesrc device=auto_null.monitor
Although it does not connect to any physical device, the volume of the null 
monitor is still controlled by PulseAudio and keyboard volume controls.  

Likewise, to see a list of ALSA outputs (sinks such as DACs) use the command: 
   aplay -l
or
   aplay -L
The arecord and aplay commands can be used to list the inputs and outputs on 
your own system whenever you need to find that information.

ROUTEs and TEEs - Defining the Audio Flow
------------------------------------------------------------------------------
The audio flow is mapped from a SYSTEM_INPUT to one or more CLIENT_SINKs. 
Between the SYSTEM_INPUT and the CLIENT_SINK the audio flow is described by a 
collection of ROUTEs. 

One way to think of routes is if they are the physical wires that are used in a 
patchbay to connect jacks (receptacles) together. If you mapped out how the 
audio flows through a crossover or other process from start to finish you could
break it down into segments (e.g. the wires) that connect nodes (e.g. the 
jacks). Nodes are where the audio begins (at a source or input), where the audio
splits (at a tee), and where the audio flow ends (at an output or sink). 

In the GSASysCon system configuration file, each route is described using the 
following nomenclature:

   ROUTE=route_start,route_end[,channel_assignment]

ROUTE_START can be an input channel number or the name of a tee. 
ROUTE_END can be the index/number of a sink, or the name of a tee
CHANNEL_ASSIGNMENT is only used when the END is a sink, and is the audio channel
   to which the ROUTE's audio should be sent. In GStreamer, channels begin with
   channel 0. A stereo DAC will have two channels: 0 and 1, a multichannel DAC
   will have additional channels. If a invalid channel is used, the pipeline
   will fail to run. 

A typical DSP crossover system uses a parallel topology. Consider just one input
channel that routes via some filters to two output channels. That would look
something like this:

   INPUT 0 --> GLOBAL FILTERS --> TEE --> FILTERS --> OUTPUT 0 ON SINK 0 
                                   |----> FILTERS --> OUTPUT 1 ON SINK 0

Channel numbering starts at 0, which for stereo audio is the left channel. The 
signal flow branches internally at a tee located in the signal flowpath 
following the global filters. The TEE is the next node in the signal flowpath. 
TEEs have one input but can have multiple outputs that are used by other ROUTEs.
I have attempted to show how the TEE above is supplying two downstream branches
in the signal flowpath or tree. Any non-reserved alphanumeric string can be used
as a TEE name, but the first character of the name must be non-numeric.  

In the example above, the signal flow consists of three routes: INPUT to TEE, 
TEE to OUTPUT 0, and TEE to OUTPUT 1. Let's give the TEE the name "my_tee". The 
corresponding ROUTE statements are then:
   ROUTE=0,my_tee #starts with channel 0 of the audio source, end at the tee
      (global filters are listed here)
   ROUTE=my_tee,0,0 #starts with the tee, ends at channel 0 of audio sink 0
      (filters for out 0 are listed here)
   ROUTE=my_tee,0,1 #starts with the tee, ends at channel 1 of audio sink 0
      (filters for out 1 are listed here)
The indenting is just for convenience and to improve readability. If any
additional output channels were needed they could all begin at "my_tee" but 
would have different values for their output channel assignments. 

So far we have defined how one input channel is split at the tee and then sent
to one of two output channels. To process stereo audio, an identical set of 
ROUTEs are needed for the other input channel (channel 1). For now just keep
this in mind. 




The SYSTEM_INPUT and CLIENT_SINKs
------------------------------------------------------------------------------
Now that we have explained the concept of ROUTEs, we can be more specific about
how to describe the sources (inputs) and sinks (outputs) in the system 
configuration file. In GSASysCon, a system may have only one input that is 
called the SYSTEM_INPUT. This is declared using the following syntax: 
    SYSTEM_INPUT = (A GStreamer source element goes here)
For example:
   SYSTEM_INPUT = alsasrc device=hw:0,0
"alsasrc" is a Gstreamer element for sourcing audio from an ALSA card or device.

GSASysCon needs to know in advance what audio rate and format should be used to 
open the SYSTEM_INPUT. You provide this information using the following three
parameters: 
  INPUT_RATE = [audio rate in Hz]
  INPUT_FORMAT = [Gstreamer audio format specifier]
  INPUT_CHANNELS = [number of audio channels in the input stream]
The audio source will be opened using the values provided by the user. If no
values are provided, the following default values will be used:
  INPUT_RATE = 48000
  INPUT_FORMAT = S16LE
  INPUT_CHANNELS = 2
When you want to open the SYSTEM_INPUT with other values for these parameters, 
simply include these statements before the SYSTEM_INPUT line in the system 
configuration file. 
NOTE: the audio format specifier for GStreamer based systems omits the 
underscore character used by ALSA. The most common formats for audio devices 
will be F32LE, S32LE, S24LE, and S16LE.

A GSASysCon system can have one or more sinks. The CLIENT_SINKs connect the 
output channels produced by the ROUTEs to external devices such as DACs. Each 
CLIENT_SINK is defined using the syntax:
   CLIENT_SINK = (GStreamer sink element goes here)
For example:
   CLIENT_SINK = alsasink device=hw:1,0
The sample rate and audio format for a CLIENT_SINK are specified in manner that
is similar to the system input, using the parameters: 
   SINK_FORMAT = (GStreamer audio format specifier)
e.g.
   SINK_FORMAT = S16LE
and 
   SINK_RATE = (sample rate in Hz)
e.g.
   SINK_RATE = 96000
When these parameters are not provided, GSASysCon automatically sets them to the
upstream parameters, e.g. the INPUT format and rate parameters. 

Using all of these together in the configuration file might look like this:
   SINK_FORMAT = S32LE
   SINK_RATE = 96000
   CLIENT_SINK = pulsesink device=XXXXX
Note that for Pulse Audio or pipewire-pulse the device string may be a long
descriptive text. You can determine the available sinks using the command:
   pactl list short sinks 

For complete documentation about how to specify the audio input and output,
please consult the help doc "Audio Sources and Sinks". 


Adding DSP Processing
------------------------------------------------------------------------------
So far we have talked about:
   INPUT --> ROUTING --> OUTPUTs
Or more specifically:
   INPUT0 --> GLOBAL FILTERS --> TEE --> FILTERS --> OUTPUT 0 ON SINK 0 
                                  |----> FILTERS --> OUTPUT 1 ON SINK 0

Recall that INPUT, TEE, and OUTPUT are all nodes in the audio flowpath and that
ROUTEs connect nodes. Any number of DSP filters that the user desires can be 
inserted in between nodes, that is to say "along" one of the ROUTEs in the audio
flowpath. This is done by listing the filters, one filter per line, under the
ROUTE statement in the system configuration file.

For example, the "global filters" lie along the route between the input and the
tee. From our example, that ROUTE statement is:
   ROUTE=0,my_tee 
Let's say we wanted to use three DSP filters, such as three EQ bands, as part
of our global input EQ. They would just be listed like this:
   ROUTE=0,my_tee
   SOME_PEQ_1
   SOME_PEQ_2
   SOME_PEQ_3
You can keep adding as many filters as you wish, just by listing them as shown.
Do this for each ROUTE, for the filters that you want to act on the audio that
is flowing along that route. For example, let's say we are making a loudspeaker
crossover with OUTPUT 0 connected to the tweeter (via an amplifier) and OUTPUT
1 will be connected to the woofer. The crossover filters mike look something 
like this:
   ROUTE=my_tee,0,0
   TWEETER_FILTER_1
   TWEETER_FILTER_2   
   ROUTE=my_tee,0,1
   WOOFER_FILTER_1
   WOOFER_FILTER_2
   WOOFER_FILTER_3 
The program simply reads down the list of filters in the file and constructs a
filter chain from them. 

So far I have used fake names for any DSP filters. In the next section I will
explain how actual DSP processing filters are described.




DSP Statements - Specifying different DSP Filter Types
------------------------------------------------------------------------------
Instead of TWEETER_FILTER_1 or WOOFER_FILTER_3 let's now implement some real-
world DSP. Let's say for the tweeter we wanted to use:
  a high pass 4th order Linkwitz-Riley filter
  reduce the gain and use inverted signal polarity
and for the woofer:
  a low pass 4th order Linkwitz-Riley filter
  a PEQ band
  a high pass subsonic filter
In GSASysCon you can use shortcut names for these filters like this:
   
   ROUTE=my_tee,0,0 #the tweeter's DSP filters are listed below:
   LR4_HP XoverF=2750
   GAIN-AND-POLARITY dB_gain=4 signal_polarity=-1 
   
   ROUTE=my_tee,0,1 #the woofer's DSP filters are listed below:
   LR4_LP XoverF=2750
   Parametric-EQ-Filter CenterF=950 Qfactor=2.2 dB_gain=-2
   BUT2-HP XoverF=30 

There is lots of new info and it is a bit dense. Keep in mind you can insert 
blank lines anywhere or use comments that begin with the hash symbol '#'. 

The filter statements are called short cut names in GSASysCon. You can read more 
about that later. These often take a parameter, e.g. in this case the
parameter XoverF that is set to the desired crossover frequency. Other 
parameters might be used, depending on which filter you choose. So in the 
example above we have:
LR4_HP XoverF=2750 --> this is a 4th order LR highpass filter at 2.75kHz
GAIN-AND-POLARITY dB_gain=4 signal_polarity=-1 --> this changes the gain by +4 
dB and sets the signal polarity to inverted. 
LR4_LP XoverF=2750 -> this is the matching LR4 lowpass filter
Parametric-EQ-Filter CenterF=950 Qfactor=2.2 dB_gain=-2 -> this is a PEQ filter
BUT2-HP XoverF=30 -> a subsonic filter at 30 Hz

                Writing Your First system_configuration File
________________________________________________________________________________



The main goal up to this point was to show how DSP filters is described in the 
system configuration file. Earlier we showed how to write inputs and outputs for
the system, and to describe the signal flow via ROUTEs. These elements can be 
combined to perform a wide variety of signal processing tasks. In this section I 
will run through the steps of how to actually write your first new system 
configuration file using an example of a multi-way loudspeaker crossover.

An easy way to create a new system is to start with an existing one. After 
installing GSASysCon the only system present is "first test". This working
system can be used as a template as described below. 

I am attempting to write this example without knowing what sort of audio devices
are present on your system. As a result I will describe a hypothetical USB audio
interface called "USB". One of the main hurdles for the new user is identifying
the input and output channel assignments for what ever audio device will be
used, especially if it can have more than 8 input or output channels. These 
channels must be specified as part of the ROUTEs but are sometimes no just 
sequentially numbered. If your system does not run, it could be that you are 
using the wrong channel assignments. 

Luckily there are some useful tools for this purpose that are supplied as part
of the GSASysCon package. Please consult the document "Using the ALSAINFO app"
for detailed information about how to perform these one time steps. For now we 
will proceed as if these have already been done and that the input and output 
channels are numbered sequentially, starting with channel 0.


Create a Folder for the New System and Use First Test as a Template
------------------------------------------------------------------------------
The system configuration file is always named "system_configuration" and is 
placed into a directory that is created in system_control/system_info. Anytime
you would like to create a new system, create a new directory in the folder:
system_control/system_info
The folder name is what will become the system name when you run GSASysCon in
the run-continuous mode. For spaces, used underscores in the folder name.
In the new folder, you can start a new system_configuration file from scratch  
or copy an existing system_configuration file from another system and paste it
into the folder.  

For example, to add a system called "my_new_system" first navigate to the dir
called system_control/system_info within your GSASysCon installation tree. Next,
create a new directory:
   mkdir my_new_system
Now simply copy the existing system control file from first test into it:
   cp first_test/system_configuration my_new_system/system_configuration

The actual name of the directory containing the system_configuration file is not
important to GSASysCon. It is just a way to separate and identify each system
configuration file. The system directories can be renamed at will, even when 
GSASysCon is running (but not when that system is running!). If you decide to 
change the name of your system later, you can do that simply by renaming the 
directory that contains the system_configuration file. Also, the system 
directories can be copied or moved in and out of system_control/system_info at 
any time, for example to periodically keep a record of the system when changes 
are being made to it.


An Example Crossover: A 3-way Stereo Loudspeaker

In this example we will describe a 3-way loudspeaker crossover with a parallel 
topology similar to the example presented earlier in the section about ROUTEs 
and TEEs. To specify the digital signal processing, "shortcut names" of a few 
common loudspeaker crossover filters are used. These are available to users of 
GSASysCon via filter definition files that are located in the filter_defs 
directory. 

If you have not done so already, open the system configuration file from the
my_new_system directory with an editor of your choice. You can simply edit the 
existing contents, but for this example we will start over from scratch. Delete 
the file contents and then paste in the following text (between but not 
including the begin file and end file lines): 
============================== begin file =====================================

#Import some filter definitions:
INSERT_FROM_FILE Common_Loudspeaker_Crossover_Filters.txt
INSERT_FROM_FILE Equalization_Filters.txt

#describe the audio input to the system:
INPUT_RATE=96000
INPUT_FORMAT=S16LE
SYSTEM_INPUT = alsasrc device='hw:CARD=USB,DEV=0'

#describe the audio output for the system:
CLIENT=LOCAL_PLAYBACK
CLIENT_SINK= alsasink device='hw:CARD=USB,DEV=0'

#global EQ filters:
ROUTE=0,LEFT_INPUT; 1,RIGHT_INPUT
  2nd-Order-High-Shelf CenterF=300 Qfactor=0.6 dB_gain=-5    #baffle-step EQ
  2nd-Order-Low-Shelf CenterF=70 Qfactor=0.6 dB_gain=3       #bass boost
  Parametric-EQ-Filter CenterF=1200 Qfactor=2.2 dB_gain=-2

#woofer output on channels 0 and 1
ROUTE=LEFT_INPUT,0,0; RIGHT_INPUT,0,1 
  GAIN-AND-POLARITY dB_gain=4 signal_polarity=-1
  LR4-LP XoverF=450

#midrange output on channels 2 and 3
ROUTE=LEFT_INPUT,0,2; RIGHT_INPUT,0,3 
  LR4-HP XoverF=450
  BUT3-LP XoverF=2750

#tweeter output on channels 4 and 5
ROUTE=LEFT_INPUT,0,4; RIGHT_INPUT,0,5 
  GAIN-AND-POLARITY dB_gain=-3.5
  BUT3-HP XoverF=2750
 
#The sink has 8 channels but only 6 channels are used by the crossover.
#  Unused channels on the sink must be explicitly declared, so we
#  send muted audio to the last two output channels
ROUTE=LEFT_INPUT,0,6; RIGHT_INPUT,0,7 #unused output on channels 6 and 7 
  volume volume=0 #this is a GStreamer element for setting the audio level

=============================== end file ======================================

Now save the file.

OK, wow, that is a lot of new stuff! Let's walk though it line by line and 
explain each section a bit.

The file starts with two instances of the INCLUDE_FROM_FILE directive. This is 
described in more detail in the "GSASysCon Advanced Topics" doc. Including
these files that are supplied with GSASysCon permits the use of the shortcut 
names for crossover and EQ filters.

The next couple of lines describe the audio source. First, the lines with 
INPUT_RATE and INPUT_FORMAT set the parameters for the input. It is a good idea
to always include these lines, even if you will use the default values. Then the
input is specified as the ALSA card called "USB".

Following that, the next few lines describe the audio sink. By writing 
   CLIENT=LOCAL_PLAYBACK
we set the sink to an audio device on the local computer. The next line
   CLIENT_SINK= alsasink device='hw:CARD=USB,DEV=0'
specifies exactly which audio device to use. Again we use the ALSA card USB.
Since the sink rate and format specifiers have been omitted, these retain the
values that were assign to the system input.

The remainder of the file describes the audio flow and the DSP filtering that 
the crossover will be performing. For the 3-way loudspeaker, the filters 
implement an LR4 crossover at 450 Hz and a 3rd order Butterworth crossover at 
2.75k Hz. In addition, there are a couple of global filters that act on the 
inputs before any crossover filters are applied. Let's look at that in more 
detail now:

Recall earlier in this file when the concept of ROUTEs was introduced, the 
following audio flowpath was discussed:
   INPUT0 --> GLOBAL FILTERS --> TEE --> FILTERS --> OUTPUT 0 ON SINK 0 
                                  |----> FILTERS --> OUTPUT 1 ON SINK 0

With our new system we have something similar but with two input channels. It 
has a structure like this:
   INPUT0 --> GLOBAL FILTERS --> TEE --> FILTERS --> OUTPUT 0 ON SINK 0 
                                  |----> FILTERS --> OUTPUT 2 ON SINK 0
                                  |----> FILTERS --> OUTPUT 4 ON SINK 0
                                  |----> FILTERS --> OUTPUT 6 ON SINK 0
and also: 
   INPUT1 --> GLOBAL FILTERS --> TEE --> FILTERS --> OUTPUT 1 ON SINK 0 
                                  |----> FILTERS --> OUTPUT 3 ON SINK 0
                                  |----> FILTERS --> OUTPUT 5 ON SINK 0
                                  |----> FILTERS --> OUTPUT 7 ON SINK 0

Input 0 and 1 are the left and right input channels. Each input routes to a tee
and then to four output channels numbered 0-7. Our crossover will use the same 
set of filters for both the left and right speakers. Making two identical
lists make the file long, hard to read, and it is easy to make a mistake or 
change only the left or right set of filters. In GSASysCon we can reduce the 
number of statements by half by listing the ROUTEs as well as their filters 
together. This is called "co-listing" the routes. For example, we have done 
that by writing:
   ROUTE=0,LEFT_INPUT; 1,RIGHT_INPUT
This line is describing two routes, separated by a semicolon. The first route is
   0,LEFT_INPUT
This connects the input channel 0 to a TEE called "LEFT_INPUT". I called it
that because when you use it later it is easy to see that this tee is fed by
the left input channel. Similarly:
   1,RIGHT_INPUT
connects input channel 1 to a tee called RIGHT_INPUT.

The output from the tees LEFT_INPUT and RIGHT_INPUT feed the remaining ROUTEs 
that make up the three branches of the crossover. Now that you are a bit more
familiar with the format, you should be able to read through the rest of the 
file and understand what is going on for each ROUTE and its DSP filters. 

The last two lines deserve a comment. Our hypothetical ALSA card called "USB" 
with 8 output channels does not have a 6 channel mode so we must use 
the mode with the next higher number of channels (all 8 channels). The crossover
is for a stereo 3-way loudspeaker, e.g. 6 channels and this leaves 2 channels 
unused. GSASysCon will not fill these channels automatically. Because all 
channels of a given mode for an output device must have audio routed to them, 
you must also feed something to the two unused channels. Here we connect the
audio from the LEFT_INPUT and RIGHT_INPUT tees to these output but mute the 
audio using the Gstreamer element 'volume'. 

Note that comments are used throughout the file. A comment is any text after the
hash character '#'. Using comments helps to keep track of what is going on and
make the file more readable. Any number of blank lines can be used to keep
different parts of the file separate from one another and will improve the
readability. 


THE EXAMPLE DOESN'T WORK FOR ME! NOW WHAT?
------------------------------------------------------------------------------
If you tried to run my_new_system it is very likely that it produced an error 
message or nother happened. Whiskey Tango Foxtrot! But remember, I made up
some "fake" ALSA card called USB in order to write the system configuration 
file. There is probably no such card on your system, or it has some other set of
channel count, etc. You need to change the SYSTEM_INPUT and CLIENT_SINK to match
the audio sources and sinks that are available on your own computer. 
 
Since I have written detailed instructions on how to do that elsewhere I will
simply refer you to those documents now. Please see the following docs, located
in the help directory within the GSASysCon file tree:

  Audio Sources and Sinks.txt - this help document describes how to check your 
  system to see what audio hardware and sources are present. We briefly touched
  on this topic way back at the beginning of this document in the "Getting 
  Started" section, but there is more complete info available in the help file.
   
  ALSAINFO.sh - this helper program that is found in the scripts directory. Once 
  you have identified the audio source you wish to use, this script helps you 
  confirm the number for input and output channels. See the help file "Using 
  the ALSAINFO App.txt" in the docs directory for usage information.

                      How to Run a System using GSASysCon
________________________________________________________________________________

After you have created the system_configuration file that describes what the 
system should do, you have to launch the GSASysCon script to run the system (to
make its routing and DSP active). 

There are several different modes that GSASysCon can operate in. I suggest using
the run-continuous mode because it gives you some feedback on whether the system
is running, and can display error messages to the user. You can find detailed
information about the various run modes in the help document called "Command 
Line Help.txt". 

To run GSASysCon in run-continuous mode, you add the following two command line
parameters:
  --config_file=filename  : filename points to the configuration file
  -r NNN                  : This tells GSASysCon to use the run-continuous mode,
                              and to refresh the display every NNN seconds

The script file is called GSASysCon.sh (note, this is case sensitive) and is
located in system_control/scripts, so the command looks like this:

system_control/scripts/GSASysCon.sh --config_file=minimal_config.txt -r 20

You will see the same sort of display that was shown when you ran the "first
test" at the end of the install script, except that your new system(s) should 
also appear in the list. Enter the system number to toggle it on and off.

          Fixing Mistakes - Error Checking and Debugging your Systems

________________________________________________________________________________

Sometimes your GSASysCon system does not run. Don't panic! How you can figure
out what is wrong? This is the process of debugging. The source of the problem
could be as simple as typing mistakes or other fatal mistake with a parameter
or other input in your system_configuration file. Luckily there are some useful
tools to help you figure out what needs to be fixed. These include the logfile 
that can be found in the directory system_control/log as well as debug output 
that Gstreamer produces. Where to find these files and how to use them for 
debugging is covered in detail the GSASysCon Advanced Topics document, in the 
section "Error Handling and Debugging with GSASysCon and GStreamer". 

To put GSASysCon into a debug mode, the user can press the key "d" (for debug 
no-run) or "D" (for debug-run). These modes will generate the Gstreamer debug 
output files - they are not produced when GSASSysCon is operating normally. You
can also look at the Gstreamer pipeline command string that is written to the 
terminal in both debug modes and try to find an obvious error. Sometimes 
tracking down a mistake or error can be time consuming and frustrating, however, 
the debug output files can make this task much easier. Please see the section on
Error Handling and Debugging in the Advanced Topics document to become familiar
with how to generate and use these files.
